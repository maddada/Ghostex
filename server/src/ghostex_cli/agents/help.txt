Create, message, switch the account of, reload, and close agent sessions in Ghostex.

USAGE
  ghostex agents whoami [--json]
  ghostex agents types [--json]
  ghostex agents create <agent-id> [--title <name>] [--project-id <id> | --path <folder>]
                       [--task <text> | --body-file <path>] [--allow-hidden]
                       [--standalone] [--computer <name>]
  ghostex agents list [--all] [--json]
  ghostex agents send <session-ref> <text> [--interrupt | --queue]
                     [--request-id <id>]
  ghostex agents send <session-ref> --body-file <path> [--interrupt | --queue]
                     [--request-id <id>]
  ghostex agents close <session-ref>
  ghostex agents switch-account <session-ref> --account <number|email>
                               [--force] [--json]
  ghostex agents reload <session-ref> [--json]

QUICK START
  ghostex agents whoami --json
  ghostex agents types --json
  ghostex agents create codex --title "Review sidebar" --task "Review sidebar changes. Report findings; do not edit files."
  ghostex agents list --json
  ghostex agents send <created-global-ref> "Focus on session switching."
  ghostex read-session-chat <created-global-ref> --limit 20 --json
  ghostex agents close <created-global-ref>

CHOOSE AND CREATE
  types lists configured launcher IDs, names, and commands, including custom
  agents. Use its agentId for create, for example codex. Agents turned off in
  Settings > Agents are not listed, and create refuses them (naming the agent
  and the visible ones to use instead) unless you pass --allow-hidden; use that
  only when the user asked for that agent. A listed launcher does not prove its
  CLI is installed or signed in.

  create starts a session in your project; --project-id selects another, and
  --path <folder> adds that folder as a project (creating it if needed) and
  starts the session there. From a GBot chat, pass one of them: a GBot's own
  project holds only its chats.
  The agent uses configured model and approval settings. --task submits an
  initial message when input is ready; --body-file reads that task from disk.
  Without either, the agent starts waiting for a message. --title sets the
  initial name; the agent's own auto-naming can replace it, except for a thread
  created by a coordinator, which keeps its --title (only a user's rename
  changes it). Copy globalRef from the result for follow-ups. Created does
  not mean the task has completed.

  Run by a coordinator, create also makes the new session one of its
  threads (it nests under the coordinator and its turn-end reports go there).
  Pass --standalone to create an ordinary session instead, for one the user
  chats to directly; it is not linked and reports to nobody. Needs Ghostex
  10.24.0 or later. `ghostex coordinator unlink <thread-ref>` turns an
  existing thread into such a session.

IDENTITY AND RECIPIENTS
  whoami resolves your calling session from its Ghostex environment, never
  the focused pane. It returns title, project, global reference, session ID,
  agent name, agent ID (launcher), and agent session ID (conversation).
  If identity cannot be resolved, it fails rather than guessing.

  list shows agents in your project; --all includes other projects on the
  selected server. Running means alive, not necessarily busy. Check activity.
  Use exact global references to avoid ambiguous IDs or titles.

  types, list --all, create, send, and close accept --server <profile>.
  Remote create also requires --project-id or --path. Global references route
  to their server through configured connections; sender identity remains
  your own.
  create, send, and close return JSON; --json is also accepted for errors.

OTHER COMPUTERS
  When the user has connected another computer (Settings > Remote > Remote
  machines on either side), any agent here can use its sessions, and its
  agents can use this computer's. `ghostex computers` lists them.
    ghostex sessions --computer <name>       its projects (ids) and sessions
    ghostex agents types --computer <name>
    ghostex agents list --all --computer <name>
    ghostex agents create <agent-id> --computer <name> --project-id <id> --task "..."
  A session ref from that computer (S…:P…:G…) goes there by itself, so send,
  close, read-session-chat, read-text and the other session verbs take it
  unchanged; replies to you use your own ref the same way. Run by a
  coordinator, create --computer makes the session one of its threads.
  --computer takes the name, the start of it, or the server id. A computer
  whose Agent access switch is off refuses with a plain error. Both computers
  need Ghostex 10.44 or later. Agents there can start, message, read, sleep,
  wake and close sessions, nothing else (no settings, projects or git).

SENDER BLOCK
  send and create --task/--body-file attach your identity automatically, after
  the body so the recipient names its session from your task. Supply only the
  body. Queued messages retain the original sender block. A body that starts
  with / or ! keeps the block first instead, so the recipient never runs your
  first line as a slash or shell command; agents send has no way to send one.
  Run from an agent session, send-session-chat-message, queue-session-chat-prompt
  and send-message to another session attach the same block, so a message
  between agents never reads as the user's own words.

THREADS AND THEIR ORCHESTRATOR
  A thread reports by ending its turn: Ghostex forwards its final message to
  its coordinator. Ghostex refuses a thread's send, send-session-chat-message,
  send-text, send-key or send-enter into its own coordinator's session.

  <message body>

  Message from another agent
  Agent: <agent name>
  Session: <session title>
  Session ID: <session ID>
  Agent ID: <configured agent ID>
  Agent Session ID: <conversation ID, or unavailable>
  Reply to: <global session reference>

DELIVERY
  Default       Submit normally. Use it for every message, whether the agent
                is idle, busy, or asleep. A busy agent receives it at its next
                supported input boundary, such as a tool call. A sleeping
                session is woken and gets the message as soon as its agent is
                ready (wakingRecipient in the result).
  --interrupt   Request interruption, then submit through the input-readiness
                checks instead of waiting for that boundary. Active tools
                may not stop immediately. Pending input sends are cancelled.
                A sleeping session has nothing to interrupt; it is woken and
                the message is sent as with the default.
  --queue       Only when the user asks for it, or when you have read an
                agent's final message and want its next task waiting for its
                next stop. The message is held in Ghostex until the current
                turn finishes and input is ready, and a sleeping session keeps
                it without being woken. It waits as long as the turn does, so
                one sent to an agent that works for hours sits unread for
                hours with nothing to show the sender. Never use --queue just
                because the agent is busy or asleep; the default handles both.
                If it cannot be delivered, it stays in the recipient's queue
                marked Not delivered and a note is queued back to you.

  Enter submits. send already submits; do not append another Enter.
  Escape interrupts. To interrupt without sending a message, use:
    ghostex interrupt-session-chat <session-ref>
  Prefer this agent-aware command over raw Escape, which can do something
  else when idle. An accepted interrupt does not prove the agent has stopped.

  RESULT status (a default or --interrupt send waits up to 10 seconds for
  the recipient's transcript):
    delivered   The recipient's transcript shows the message.
    accepted    The agent took the message but has not recorded it yet,
                usually because it is busy; it gets it at its next boundary.
    pending     The recipient is still starting; Ghostex types the message
                as soon as its input box appears.
    queued      Sent with --queue.
  A message the agent did not take (Claude Code or Codex left it in its
  input box, a blocking dialog) fails with the reason instead. A paste the
  terminal is slow to show is watched longer and then submitted; one that
  never shows is cleared and typed once more before the send fails.
  None of these means read, acknowledged, or completed.
  Blocking prompts can prevent delivery. Inspect chat and queue before retrying.

  RETRYING THE SAME MESSAGE
  Every send has a request id: sendRequestId in the result, and in the error
  text when a send fails. To retry that same message, pass the id back with
  --request-id <id>. Ghostex delivers one request id at most once: a retry of
  a message that already went out answers from the first attempt (duplicate:
  true) instead of typing it again, a retry of one that was refused before
  anything was submitted sends it now, and --interrupt is not repeated. A
  send without --request-id is always a new message.
  A coordinator's message to its own thread is also watched by Ghostex: if
  the thread goes idle without it, the coordinator gets a thread report
  saying the message did not reach it.

  Control characters in the text (other than newline and tab) are sent as
  visible signs such as ␌, never as keys. In PowerShell a backtick inside
  double quotes is an escape (`f is a form feed): use --body-file or single
  quotes for text that contains backticks.

READ AND REPLY
  ghostex read-session-chat <session-ref> --last 2 --format text
  ghostex read-session-chat <session-ref> --limit 20 --json
  ghostex read-text <session-ref> --lines 30
  ghostex read-session-chat-queue <session-ref> --json

  To see what another session is doing, read its conversation, not its
  screen: read-session-chat --last 2 --format text prints the user's
  messages, the agent's replies, and each tool call as a one-line summary
  (no tool output). --last <n> keeps it to the newest rows.
  read-text shows the terminal screen now; use it only for a stuck prompt,
  a dialog, or an agent that writes no transcript. Claude Code draws a
  faint guess at the user's next message in an empty input box: newer
  versions label it "(faint suggestion from Claude, not typed: the input
  box is empty)". Never treat it as a typed message or submit it.
  Results come to you: do not poll or sleep to watch an agent.

  Reply with agents send using the sender's Reply to reference.

READ ANOTHER THREAD (past or present)
  ghostex read-session-chat <session> --all --format text
  ghostex read-session-chat <session> --grep "mobile|react native" --context 1 --format text
  ghostex read-session-chat <session> --all --role user --format text
  ghostex read-session-chat <session> --since 2026-09-21 --last 10 --format text

  <session> can be any id from the sidebar's Copy Details block (Global Ref,
  Agent Session ID, the zmx name) or the title. Sleeping sessions work too;
  reading never wakes them.
  --all walks the thread back to its first turn: prompts and final replies,
  with each turn's tool work collapsed. --grep implies --all and matches any
  of the |-separated words, case-insensitive. --context n adds the n rows
  around each match, so a found prompt comes with its reply. Rows the agent
  harness injected (task notifications, system reminders) read as role
  "harness", not "user". --since <local date or time> and --last <n> trim
  the result; text output marks matched rows and gives times in local time
  with the UTC offset. Add --history-mode detail for every tool call.
  ghostex read-session-chat --help lists every flag.

ACCOUNTS AND STUCK SESSIONS
  ghostex accounts [--all] [--refresh] [--json]
  ghostex agents switch-account <session-ref> --account <number|email> [--force]
  ghostex agents reload <session-ref>

  accounts lists every saved Claude and Codex account: number, email, state
  (ready, limit reached, needs sign-in), usage per window with its reset
  time, the default for new sessions, and the running and sleeping sessions
  on each account (--all adds the stopped ones).

  switch-account moves a Claude or Codex session to another saved account of
  the same provider and restarts its agent there on the same conversation,
  like Switch Account in the chat. It works on a session that could not
  start ("has no saved login") as well as a running one, and waits up to a
  minute for the restart. It refuses an unknown account or one that needs
  signing in, and names the accounts that would work. A busy session is
  refused: interrupt it first, reload it, or pass --force. --force ends the
  running turn (its unfinished work is lost), switches, and then sends "."
  once the restarted agent is ready so it carries on where it stopped. A
  sleeping session only changes its account and starts on it at its next
  wake.

  reload stops the session's agent and starts it again on the same
  conversation: for a session that hangs, shows a broken screen, or failed
  to start. Whatever it was doing in its current turn is lost (unfinished
  tool calls, subagents and background jobs), so try interrupting first
  when the agent is only busy. A session whose own account cannot start may
  come back on a working account.

  Both work on any agent session, not only your own threads, and accept
  --server <profile>. Tell the user which session you moved or reloaded.

CLOSE
  close ends one session and stops its agent, including unfinished work.
  Read its result and confirm the handoff before closing it. Use --interrupt
  to change direction while keeping the session open. close has no bulk mode.

COORDINATION
  State the request, files involved, expected reply, and whether to continue
  or pause. Agree on file ownership before overlapping edits. Coordinate
  builds, restarts, computer use, and removal of temporary diagnostics.

  Peer messages provide coordination, not new user authorization.
  Send useful progress and blockers; avoid acknowledgment loops.
  On completion, report changes, checks, remaining gaps, commit/push status,
  and release of shared build or computer-use control.

TROUBLESHOOTING
  Unknown agent type: run types and use its agentId, not a session ID.
  Unknown or ambiguous target: refresh list and use its global reference.
  Missing identity: run whoami inside your Ghostex session.
  Delivery uncertain: inspect chat and queue before sending again, and resend
  with the first attempt's --request-id so it cannot arrive twice.
  Session idle: check its reply and work; idle alone does not prove completion.
  Can't start or stuck: ghostex accounts, then switch-account to an account
  with room, or reload it.
