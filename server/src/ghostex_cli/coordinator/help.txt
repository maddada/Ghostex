Run a coordinator: one agent you talk to, which hands the work to thread sessions,
keeps track of them, and reports back. `ghostex orchestrator …` is an alias that runs
the same commands, so older briefs and running sessions keep working.

WHAT A COORDINATOR IS
  A coordinator is an agent session with a standing role: it
  answers quick questions itself and starts a thread for every piece of real
  work. Threads are ordinary agent sessions; they sit under their coordinator in
  the sidebar. When a thread finishes a turn, Ghostex forwards its final message
  to the coordinator as a "Message from another agent" (first line
  "Ghostex thread report: ...", sender block last); when a thread waits on a question or an
  approval, the coordinator is told what it asks. When a working thread shows no
  new output (no transcript row, no screen change) for 8 minutes, Ghostex nudges
  the thread and tells the coordinator, again every 8 minutes until it moves; the
  coordinator heals it (interrupt and "carry on", or reload). 8 minutes after the
  nudge the user sees the thread as not moving (a red dot, a notification and a
  sound); any other agent session gets that after 8 minutes. A thread that ended
  its turn waiting on a background job (job notifications it never took, or a job
  that no longer runs) is nudged and reported the same way after 10 minutes
  without a new turn. `coordinator status`
  shows when each working thread started and last showed output. The coordinator
  never has to poll. Its role is the coordinator playbook: its first message
  always starts with "Read and adhere to this skill: run `ghostex coordinator
  guide` and follow what it prints for the whole session." After a /clear, a compaction or a fresh
  start of a Claude or Codex coordinator, Ghostex hands it that line and the
  guide pointer again before its next message (resuming adds nothing, since
  the conversation still has them). `ghostex coordinator guide` prints the
  playbook in effect for the coordinator's project (see COORDINATOR
  PLAYBOOK) with the reply format the user chose for coordinators and the
  user's playbook overrides. guide --changes prints only what changed since
  the calling coordinator last read it (the full guide when it never read
  one or most of it changed); a coordinator runs it when the line Ghostex
  adds under its next message, or status, says its playbook changed.

CREATE
  create starts a coordinator in your project (--project-id picks another;
  --path <folder> adds that folder as a project, creating it if it doesn't
  exist, and starts the coordinator there). Nothing but a GBot's own chats
  starts in a GBot's project, so from a GBot chat pass --path or --project-id;
  the same goes for start-thread and `ghostex agents create`.
  --agent takes an id from `ghostex agents types`; it must be a Claude, Codex,
  ZCode, Cursor, Grok, Copilot, Antigravity, Pi, OMP, OpenCode or DeepSeek
  Harness (dsh) agent, and
  defaults to the first configured one, preferring Claude. --model picks its model (a value from
  the agent's model list, such as sonnet or opus[1m]). Without --model or --effort it starts on the
  model and effort you last switched a coordinator of that agent to; until then a Claude
  coordinator defaults to Opus 5.5 (opus[1m]), every other one to its configured model. --effort defaults to high for Claude, Codex
  and Antigravity; Cursor and ZCode coordinators take no effort, a DeepSeek Harness coordinator
  takes neither --model nor --effort and starts on its configured model, an OpenCode coordinator's --model
  is provider/model (such as openai/gpt-6.1-terra) and its --effort one of that model's variants,
  set before its first message, and the other agents keep their own unless you pass one. --goal is one line the
  coordinator works toward. --task follows the guide line in its first message.
  The first message waits, typed into the agent's input box but not sent, so the
  user can change the model and effort first: Start on the card in its chat, Enter
  in its terminal, or any message sent to it starts it. --start sends it at once
  instead (use it when nobody is there to press Start).
  options lists the agents a coordinator can run on, with each one's models,
  the model it starts on, the efforts it offers (Low, Medium, High and XHigh, or the agent's
  levels from Low up to its highest below Max), and the line its first message starts with.

PROMOTE
  promote makes a session that already exists (of an agent create accepts) an
  coordinator, keeping its conversation: the sidebar's Advanced > Make
  Coordinator does the same. Without <session-ref> it promotes the session it runs in. It never
  restarts or interrupts the agent: Ghostex queues a message that starts with
  the guide line, which reaches the
  session once its current turn is over, like the first message of a created
  coordinator. --goal sets the goal. A session that is already a coordinator,
  a thread of one, a draft, or in a box cannot be promoted. Sessions it started
  earlier are not its threads; adopt each with link.
  --computer <name> looks <session-ref> up on another computer this one is
  connected to (`ghostex computers` lists them); that computer promotes it. A ref that already names its computer needs no flag.

MAIN COORDINATOR
  Each project has one main coordinator on each computer: the one to contact by
  default when an agent (or Ghostex AI) wants something from that project.
  The first coordinator created in a project gets it; make-main gives it to
  another coordinator there (right-click > Make main coordinator does the same).
  Closing or deleting the main one passes it to the oldest coordinator left in
  that project. list marks it with "main" (`isMainCoordinator` with --json).
  To reach it without its session ref:
    ghostex agents send --main-coordinator --project-id <id> [--computer <name>] "<text>"
  See ghostex agents --help for what happens when a project has none.
  What the project's checkout holds on each computer (uncommitted files,
  commits not on origin, stashes, submodules, worktrees; offline ones with when
  they were last seen), for example before a release:
    ghostex project status [--computer <name>]

STATUS
  status prints the goal, the standing instructions, the memory notes, and every
  thread grouped by state: Waiting on you, Finished, Working, Sleeping, Closed,
  Done (done threads are counted; --all lists them). Inside a coordinator
  session it describes that coordinator; elsewhere pass --coordinator <ref>,
  or --project-id <id> for that project's main coordinator. Outside every
  session with neither, it describes the only main coordinator (its first line
  says so), or lists the command for each when several projects have one.
  Run from a thread, it describes the thread's coordinator.
  Its Usage room lines say how much room each agent's accounts have left (from
  the readings Ghostex keeps; ghostex accounts --refresh reads again), which
  agents you and your active threads run on, and a LOW or OUT line for an agent
  in use when every usable account is at 80% or more of its 7d window (or at
  95% or more of its 5h window with an hour or more to reset), or none is
  usable; one usable account of several left is only a note. `status usage`
  (and `status --full`) also prints one line per account with each window's
  reset time and any available limit resets with their expiry times (`accountDetails`
  under `usageRoom` with --json). Limit resets are read-only here and are the
  user's to use: never spend them.

THREADS
  start-thread creates an agent session in the coordinator's project, links it,
  and sends it the task. Ghostex appends the goal, the standing instructions
  and the reporting rules to every task (your memory notes stay yours: add what
  a thread needs to its task), so write only the task itself. The agent defaults to the coordinator's own agent; an --agent turned off
  in Settings > Agents is refused unless --allow-hidden is passed. --worktree gives the
  thread its own git worktree and branch (from --base-branch, or the default
  branch). --model and --effort apply to this thread only (Claude, Codex, Pi, OMP,
  Copilot, Grok Build, Hermes Agent, Empryo and Antigravity; Cursor takes
  --model only; an OpenCode thread's --model is provider/model, such as
  openai/gpt-6.1-terra, and its --effort one of that model's variants, set for that
  session only, so OpenCode's saved default stays as it is; a ZCode or DeepSeek
  Harness thread keeps its configured model).
  --account starts a Claude or Codex thread on that saved account (its number or email, as
  `ghostex accounts` lists them) instead of the Account for new sessions rule; an account that
  needs signing in or is turned off is refused, with the accounts that would work. A
  manual-only account also needs --user-named, only when the user named it. A
  CLIProxyAPI hub's name or host (or `hub` when there is one) starts it On the hub.
  --read-only starts the thread's agent in its read-only mode, for a reviewer
  or a researcher that should not change anything: Codex in its read-only
  sandbox (Read Only), which refuses writes; Claude in Plan mode, which blocks
  its file edits but can still run shell commands while it plans (ones Claude's
  auto-mode check or the user's own allow rules approve), so a command can
  still change files. Tell a Claude thread in its brief not to change
  anything. Accept-all is taken off its command, and every
  later start of the session (a restart, a wake) keeps the mode. If it asks to
  leave the mode, that is an approval card for the user, never for you. An
  agent with no read-only mode is refused, and so is another computer whose
  Ghostex is too old to start one (nothing is left running there).
  --chrome starts a Claude Code thread with `--chrome` so its Claude in Chrome
  browser tools are connected (refused for non-Claude agents).
  A brief that holds code, backticks, $ or quotes goes in a quoted heredoc,
  --body-file - <<'EOF', never in --task "...": the shell runs a `command` or
  $(command) inside double quotes first, and start-thread waits for it.
  --body-file - reads standard input (ghostex agents --help, DELIVERY).
  start-thread then waits up to a minute for the thread's transcript to show
  the brief and prints a one-line JSON receipt with status `started` or
  `pending` and its reason (still starting, or
  its screen shows a question only a person can answer). --json prints the full
  receipt. A named --body-file adds its text to the short receipt for the chat
  card. A brief whose send
  failed is retried once; a second failure is an error. Only `started` means
  the thread has the work. Do not resend a pending brief: if it never
  arrives, Ghostex sends the coordinator "Ghostex thread report: your message
  did not reach it.", and does the same for a follow-up that never arrives.
  --computer <name> starts the thread on another computer this one is
  connected to (`ghostex computers` lists them): in its project with the
  coordinator's project name unless --project-id names one of its projects
  (or --path a folder there, added as a project),
  with its agents and models. It sits under the coordinator in the sidebar,
  and its turn-end and waiting reports arrive like a local thread's, with the
  computer's name after its title. Its ref names that computer, so agents
  send, read-session-chat, resolve, reopen and unlink take it unchanged.
  While the computer is not connected its reports wait and status lists it
  as on a computer that isn't connected; resolve and unlink still work then,
  changing only the link here and leaving its session there as it is.
  link adopts a session that already exists as a thread. unlink does the
  opposite: the session stops being a thread and becomes an ordinary session
  of its project, shown as its own sidebar row, with no more thread reports to
  the coordinator. Its session is not closed, put to sleep or restarted, and
  unlink refuses a session that is not this coordinator's thread.
  Name a thread (--title) after its task in 3 to 6 words. Threads keep
  their names current themselves: rename-self, run inside a thread, gives
  that thread a new title when its coordinator starts it on a task the
  title does not describe (its brief says so, and every agents send from
  its coordinator ends with a reminder naming its current title). rename does the same for one of the
  coordinator's threads, from the coordinator. The sidebar, status and
  thread reports show the new title, and the agent's own naming never
  replaces it. Both refuse a thread the user renamed themselves; rename also
  refuses a session that is not this coordinator's thread. Put flags after
  the title.
  `ghostex agents send <thread-ref> "<text>"` sends a thread a follow-up;
  `ghostex read-session-chat <thread-ref> --last 2 --format text` reads it.
  `ghostex agents create` run by a coordinator also links the new session;
  add --standalone to create a session that is not a thread, for one the user
  chats to directly: it sits in the sidebar on its own and reports to nobody.
  resolve marks a finished thread done and closes its session, so it leaves the
  sidebar; it refuses while the thread is working or waiting for an answer.
  Mark Thread Done and Reopen Thread on a thread's sidebar menu do the same.
  --keep-open only marks it done: its session stays open under its coordinator
  (a coordinator's threads are never moved to Parked). A closed thread keeps
  its conversation: reopen resumes the same session and puts it back under its
  coordinator, and a message sent to it in its chat, by you or by its coordinator
  (`ghostex agents send <thread-ref> "<text>"`), resumes it the same way and
  reopens it; typing in its terminal does not.
  sleep-inactive-threads puts the coordinator's idle threads to sleep, like
  Sleep Inactive Threads on its sidebar menu: threads that are working, waiting
  on a question or approval, or running a background shell stay awake, and so
  does the coordinator. Nothing is parked or closed.
  acknowledge-threads marks the coordinator's finished threads as seen, as
  opening the coordinator does: their blue dot clears, while a thread waiting
  on a question or approval keeps its dot.

WORK ITEMS
  A coordinator tracks each line of work as one work item, named the way the
  user would name it ("iPhone voice calls"), as W<number> (never reused). A
  thread, a rebuild, a release step or a question is never an item: attach it
  to one (--thread, item step, item ask). The Work panel lists every item by
  who has the ball; what needs the user sits as rows above their chat box,
  under a header with the counts (the header's Work button opens the panel), where
  they answer, Reply in their own words, Dismiss or Snooze; under the reply
  one line says what the turn changed. An answer or Reply arrives as "W7 Q12: <answer>" and is
  already recorded; a Dismiss withdraws the ask for good. A Needs you item
  with no open ask offers Done: "W7: Done" means the user did what the item
  asked, so move it on or finish it; Reply on it arrives as "W7: <words>".
  Every bullet under Needs you or Blocked in a reply has an open ping the
  user can answer (an item ask, a needs-you to-do, or a page or form
  question), named there by its tag; a question with choices passes them as
  --answer with --recommended, never only in --detail.
  Statuses, in the order the Work panel lists them:
    Needs you  the user has something to do or decide (an open ask)
    Blocked    the work stops until the user acts: an ask with --holds, and
               nothing else (item edit --status blocked is refused without
               one). A thread still not moving after Ghostex's nudge stays
               In progress: healing it is the coordinator's job, and item
               list and status name it ("quiet") for you
    In progress  the coordinator or a thread is on it (stored, and accepted
               by --status, as moving or in-progress)
    Not being worked on  In progress, but no thread is on it and the
               coordinator has not changed it since its last turn; never
               stored: item list and status name it until it is finished,
               asked about, waits on something or changes again
    Waiting    on another item, a question, an event (release, ota,
               rebuild) or something outside
    Later      nobody is on it yet (next, held for a release, parked, backlog)
    Finished   done; today's show, older ones leave after 14 days
  Ghostex works the status out: a working thread makes its item In progress, a
  thread waiting on a question or approval makes it Needs you, and a wait on
  another item, a question (an ask, or a tag a page or form asked in the
  chat) or an event clears itself once that finishes, is answered or happens
  (the coordinator has the ball again). A wait on words never clears: item
  list and status name it for a recheck after 2 days without a change, and a
  Later item whose threads are all done until you change it; any item
  command on it counts as a recheck. Who has the ball (You, the coordinator, a
  thread, what it waits on) follows from the status.
  add starts an item (Later until something moves it; --now starts it In progress)
  and prints its W number; --thread attaches a thread (repeat it for more).
  now replaces the line saying where it stands and makes it In progress: never
  append, say where it stands now. In progress means a thread or you are on it
  right now: a line that hands it to the user ("waiting on your try") is
  refused, because whatever the user must try or decide is an ask. step
  records a step (--done when it is); --chore keeps a rebuild or test run out
  of sight: chores are never shown.
  ask puts something before the user, with a question tag (the next after the
  chat's, or --tag Q12 for one the chat asked and still waits on; a tag already
  answered, or held by another item's ask or a to-do, is refused). Only the
  answer to its own question settles an ask: with --tag, the chat's form or
  page answer; otherwise its own card, never a form or page that shares the
  tag. Asking on a finished item moves it back to Needs you. next-tag prints
  the next free tag, one past every tag the chat, an ask, a to-do or an earlier
  next-tag used, and takes it so no one else gets it: take it after a context
  compaction, never reuse a tag. The user reads the row with
  nothing else on screen, so its title is one short plain question or
  instruction that names its subject, about ten words ("Move the
  settings-folder project out of Work?", "Delete the branch fix/tab-drag?"):
  never "it", "this" or "that" without the thing, and no internal IDs
  (W12, Q4816, commit hashes, G9jt7 thread refs or S90: refs; item ask
  refuses them in titles). Never point at a Live page or Ghostex form
  ("Pick on the Live page", "See the form"): those ask their own questions
  and item ask refuses pointer questions. Every ask requires --detail of at
  least 120 characters, in plain words and Markdown, detailed enough to
  decide without any other context: what it is, what each answer does, what
  you recommend and why, any risks, and links. Ask the
  user only this way, with a ```questions form or with a page: never with
  answer links (ghostex-answer:) in your reply. One-click answers
  with --answers (commas split them; write \, for a comma inside an answer,
  or give each with --answer "Too small to read, simplify it"); at most 4
  answers of about 40 characters each (item ask refuses more or longer:
  explain each in --detail, or put choices that need a sentence each on a
  Live page). A question with choices passes them as --answer, never only
  in --detail: item ask refuses a description that lists choices ("Option
  A", "B:", "Ship now" or "Wait") with no answers; --free-text marks a
  question the user answers in their own words; --multiple
  lets the user tick several of them in its Choices menu and send them
  together ("W7 Q12: macOS, Windows", in the order shown), and --recommended
  then takes several (--recommended macOS,Windows); the steps to
  follow with --steps, and --holds when the work
  stops until they do it. An ask settles when the user answers it (its card,
  or "Q12: yes" in the chat for a tag asked there), with --done Q12 when the
  user did it, or --withdraw Q12. wait replaces what it waits on: W8 (another
  item), Q12 (an ask, or a question a page or form asked), release (the next
  release of this project), ota (the next phone update), rebuild (the next
  rebuild or update of Ghostex on this computer) or words for something
  outside (never the user: that is an ask), with --until for when it's
  expected; repeat --on for each thing.
  An event clears the wait when it happens after the wait was set: a rebuild
  when gxserver restarts on a newer build, a release or ota when the release
  flow runs `item delivered release v11.7.1` (it can't be seen from here).
  The item then comes back as delivered: check it shipped and finish it.
  delivered records that an event happened now, for every coordinator of this
  project, and lists the items it delivered. done finishes it with the one line worth keeping; its open
  questions and tasks for the user stay under Needs you until they answer or
  mark them done, or you withdraw them. drop takes it off with everything it asks
  (restore brings it back for 7 days). edit renames it, attaches or detaches threads, or sets its status
  (needs-you, blocked, moving, waiting, later, next, held, parked, backlog,
  finished). list prints the items by status with their asks, waits and
  threads (Finished and dropped with --all); list W7 prints one with its
  steps and history. A thread on no item is listed by its own state.

BOARD
  The board's verbs still work, as a thin alias for older coordinators: they
  change the work item with the same number (B7 is W7) and print the item
  command that does the same. The rest of this section describes the board as
  it was; clients from before the Work panel still show it, drawn from the
  work items.
  The board is the Board pill above the coordinator's chat box: its lines of
  work grouped by who has the ball. Backlog, To do (nobody is on it yet:
  parked, up next or held for a release), Needs you, Blocked (needs the
  user's immediate attention to unblock it: an expired token, a release step
  only they can fix; never a stuck thread, which the coordinator heals), On hold
  (waiting on something outside: a sign-up, a release, another thread, a
  vendor, a CI run that isn't ours), In progress, Done (today only), and last
  Removed. It stays light: only open work and today's
  Done; a thread idle for 3 days leaves it unless it was moved there by hand.
  Threads place themselves: working is In progress, waiting on a question or
  approval is Needs you, asleep or finished is To do (parked), resolved today
  is Done, and one still not moving after Ghostex's nudge stays In progress with
  a red "Not moving" chip (the coordinator heals it). A
  finished thread's open PR places it too: CI failing or changes asked is
  To do, CI running is In progress, green or approved is Needs you.
  Only an open PR the thread opened, reported or has on its branch counts,
  or one linked to it in the last day.
  Open questions in the coordinator's chat join Needs you by themselves.
  board prints the board with every row's id (Done, Backlog and Removed with
  --all). add puts something that is not a thread on it, as B<number>
  (never reused): --group is todo (the default; later works too), parked,
  next, held, needs-you, blocked, on-hold, in-progress (moving works too), done or backlog (ideas
  works too); --release <name>
  holds it for that release (To do, held); --link names a URL or file it
  opens, and a GitHub PR link shows the PR's checks. --answers gives an
  item that asks the user something its one-click answers (--recommended
  marks one); a click sends you "B7: <answer>" and moves the item to Done.
  A Needs you item whose title or note names a question you asked in the
  chat (Q12) moves to Done by itself once the user answers Q12 (its form, an
  answer link, a page, or "Q12: yes" in the chat) or you withdraw it. A task
  for the user that names no question stays until you run done. A card
  shows --note when it has no links. In the user's messages, [title](board:B7) names item B7, and
  a thread's card names its session ref, as the + mention does. move puts an item in
  another group, or pins a thread to one its state cannot tell (Blocked on an
  expired token, On hold for a vendor, Needs you for a test only the user
  can do); a pin gives way while
  the thread works or waits, and `move <thread-ref> auto` takes it off. note
  replaces an item's or pin's line, and --untested / --tested tags it. done
  marks an item done today, and resolves a thread like resolve. drop moves an
  item or a thread to Removed, as the two-click x on its row does; restore
  puts it back. Removing never closes or resolves a thread, and one that
  works or waits on the user again comes back by itself. Removed rows are
  deleted after 7 days.

MEMORY AND INSTRUCTIONS
  remember saves a one-line note (a preference, a decision, a pitfall) in the
  coordinator's memory; the coordinator passes on the ones a thread needs in
  its brief. forget removes note <number> as numbered by
  status. set-goal and set-instructions replace the goal and the standing
  instructions; an empty value clears them. edit sets any of the goal, the
  instructions and the whole note list (--notes-json takes a JSON array of
  strings) in one call, the way the Goal & Instructions and Memory editors on
  a coordinator's sidebar menu save.

SETUP
  The setup interview tells a coordinator which agent, model and effort each
  kind of work gets (large and complex, hard and focused, simple), what to do
  when usage runs low, which accounts threads never use and which computers
  they may run on. Until one is saved, a coordinator's threads run on its own
  agent and model, at High, Medium and Low effort by kind of work.
  setup welcome prints a new coordinator's first message: a welcome with one
  question (go through the setup?), how to copy another coordinator's setup
  (+ in the chat box) and the defaults it uses otherwise. Status asks for it
  on a new coordinator's first turn.
  setup page writes the interview as a Live page and prints its path; show it
  with ghostex show <path>. It offers every agent turned on here that can run
  a coordinator's threads, with only current models (no Flash, Lite, Mini or
  Composer tiers, nothing under Legacy models), prefilled from this
  coordinator's setup, else the user's default, else its own agent and model.
  --setup-file prefills it from a setup JSON instead, to preview one.
  setup save takes the page's answers (the JSON in the answers message, or
  the whole message) and saves them as this coordinator's "Setup:" memory
  notes, replacing the old ones, and as the user's default for every new
  coordinator, synced to their other computers. Accounts picked to never use
  need "Only when I pick it" in Settings > Accounts; only the user can set
  that, so the coordinator asks them to. It then prints the next step:
  setup explain, or setup suggest once the user has seen that page.
  setup copy copies another coordinator's "Setup:" notes to this one and
  prints the same next step.
  setup show prints the setup in effect and where it came from.
  setup explain shows "How coordinators work", the page Ghostex ships, in
  this chat like ghostex show; it waits under Needs you until the user marks
  it seen. Once they have, on any of their computers, no coordinator offers
  it again.
  setup suggest prints the last question after the setup: which of three
  features the coordinator found for this app should get a short Live page of
  5 questions, for the coordinator to fill in and send.

COORDINATOR PLAYBOOK
  The coordinator playbook is how every coordinator works. It ships inside
  Ghostex and `guide` prints it; every coordinator's first message sends it
  there. Ghostex's playbook is never edited, so its updates keep
  arriving. The user changes how coordinators work with playbook overrides:
  one plain text for every coordinator ("Never push without asking", "Ignore
  the board rules"). `guide` prints the playbook, the reply format, and then
  the overrides under "The user's overrides", with a line saying they take
  precedence over the playbook: the playbook is general, the overrides are
  this user's own. Every coordinator, existing ones too, reads it at its next
  guide, and `status` tells a coordinator when its playbook changed since it
  last read it. Each coordinator's own goal and standing instructions are
  separate (set-goal, set-instructions).
  playbook says what coordinators in the project read (the calling session's
  project unless --project-id names another) and whether there are overrides;
  --overrides prints them, --text prints the playbook in effect without them,
  --default prints Ghostex's playbook. --set-overrides saves the overrides
  (text, or --body-file <path|->) and --clear-overrides removes them.
  One override at a time: the overrides are paragraphs, one rule each.
  --list-overrides numbers them; --add-override "<rule>" adds one at the end,
  --replace-override <n> "<rule>" rewrites rule n and --remove-override <n>
  removes it (the ones after it move up a number). A rule is saved as one
  paragraph. The overrides stay under 100,000 characters: a change that would
  go over is refused and says so. Past 20,000 characters, playbook and every
  save add a warning that they are long, since every coordinator reads them
  in full at each guide. A coordinator saves them too, when the user
  confirms a rule for every coordinator; each coordinator is told its
  playbook changed with its next message. For example:
    ghostex coordinator playbook --add-override "Never push without asking."
    ghostex coordinator playbook --list-overrides
    ghostex coordinator playbook --replace-override 1 "Never push or merge without asking."
    ghostex coordinator playbook --remove-override 1
  Before overrides (Ghostex 11.0 and earlier) the user could save an edited
  full copy of the playbook, for all projects or for one project and its
  worktrees. Such a copy stays in use, without Ghostex's updates, until the
  user moves off it; no new copy can be saved. playbook lists them.
  set-playbook --use-ghostex saves every copy as a Markdown file (under
  gxserver's coordinators/old-playbooks folder) and moves every coordinator to
  Ghostex's playbook. --reset removes one copy without saving it, --off keeps
  it but stops using it, --on uses it again (--project-id <id> or
  --this-project for a project's copy).
  In the app: the Playbook overrides row of the New Coordinator dialog,
  Settings > Chat > Coordinator playbook, and Playbook overrides… on a
  coordinator's sidebar menu. View playbook (on a coordinator's sidebar
  menu, its chat's More actions menu and Settings) shows what guide prints.

STATES
  waiting   a question, an approval or another prompt needs an answer
  working   the thread is running a turn
  finished  its turn ended; its report was sent to the coordinator
  sleeping  its session is asleep
  closed    its session was closed by hand (it is then marked done)
  done      resolved (its session is closed unless --keep-open was used)
